# K11 双路搜索协调结果

<!-- iris:object K11 kind=rules file=true -->

本文件是 `K11` 的正式定义位置，也是该合同唯一的正式定义位置。它约束**一次 `web_search` 动作究竟执行了几条路线、每条路线发生了什么、结果如何被表达**。责任组件是 `C20`（双路网页搜索协调），主要消费方是 `C20`、`C10`、`C18`、`C22`、`C25`。

本合同只定义协调结果：两条路线的能力来源与状态含义见 [K04](./K04-provider-capability.md)，原生受控子请求的构造与适配见 [K12](./K12-native-search-subrequest.md)，正文读取窗口见 [K13](./K13-web-reading-window.md)，候选来源与支持关系见 [K14](./K14-evidence-and-provenance.md)，交付限制说明见 [K15](./K15-delivery-result.md)，外发授权与开关见 [K09](./K09-web-authorization.md)，额度与费用记录见 [K06](./K06-budget-ledger.md)，MCP 传输见 [K18](./K18-mcp-transport.md)。工具侧的统一入口是 `T11` `web_search`（工具卡见 [tools/README.md](../tools/README.md)），其自身合同不在本文件重复。

**执行事实**：`C20` 协调器已在源码中存在并接入生产 `web_search`（`src-tauri/src/ai_runtime/dual_path_search.rs`）。`K12` 构造器与凭据解析器已落地，但生产无适配器，原生按能力事实为 `unsupported`，MCP 单路是正常配置；两路组合有机械 `V03`。关闭仍等 `D04`／`G02`。`V04` 生产入口两路仍缺（构造器存在不等于已执行原生搜索）；不得把两个替身都被调用写成 `V04`，也不得把 MCP 主备写成双路。原生端点的兼容与费用适配**仍未验证**（`Q17`／`G03`），本体系不宣布 MiniMax、DeepSeek 或 Gemini 任一端点已通过。

## 接口

**输入**：

| 输入           | 含义                                             | 来源                             |
| -------------- | ------------------------------------------------ | -------------------------------- |
| 请求身份       | Run ID、输入修订号、本次搜索动作身份、父调用 ID  | `C01`／`C03`                     |
| 模型提出的查询 | 关键词、时间与地域约束等                         | 主模型提议（`C16` schema）       |
| 外发批准       | 本次查询与外发范围是否获准                       | `C04`（`K09`）                   |
| 两路能力       | 原生搜索与 MCP 搜索各自的支持状态                | `C10`（原生）、`C18`（MCP 服务） |
| 额度           | 本次动作可用的资源租约                           | `C13`（`K06`）                   |
| 配置快照       | 原生能力配置、MCP 有序候选与抓取能力，带配置版本 | `C10`／`C16`／`C18` 合成         |

**输出**（逻辑结果，字段固定）：

| 字段               | 含义                                                       |
| ------------------ | ---------------------------------------------------------- |
| 请求身份           | 本次搜索动作的关联标识（Run、修订、动作、尝试）            |
| 各路线 `supported` | 该路线在当前模型／端点／配置下是否可用                     |
| 各路线 `attempted` | 本次动作是否真的发起过该路线                               |
| 各路线 `succeeded` | 该路线是否取得可核实的检索结果                             |
| 各路线 `failed`    | 该路线的失败分类；与 `succeeded` 分开记录                  |
| 候选来源           | 各路返回的候选 URL 与渠道来源标记                          |
| 用量               | 本次动作的实际请求、token、时间与费用计数（归 `C13` 账本） |
| 不足说明           | 为何本次未能满足双路合同，或缺哪些证据                     |

**执行证据的接受条件**：只接受**供应商定义的实际搜索事件**或**能证明检索发生的结构化 grounding 元数据**。单纯发出带工具声明的请求、模型自行生成 URL，都不算已搜。结构化检索凭据用于证明供应商按其协议报告了检索，不是不可伪造的真值证明，也不证明返回内容正确或来源彼此独立。

## 状态转换

本合同不引入新的运行时状态机；它把两路状态的合法组合固定下来，放在同一请求身份下：

| 情形                     | 合法状态组合                                           | 结果表达                                         |
| ------------------------ | ------------------------------------------------------ | ------------------------------------------------ |
| 原生与 MCP 均可用        | 两路 `attempted=true`；各自 `succeeded`／`failed` 独立 | 两路真实执行；合并候选、去重、保留渠道来源       |
| 原生不支持（正常配置）   | 原生 `supported=false`、`attempted=false`；MCP 单路    | 正常单 MCP，不显示能力降级                       |
| 原生临时失败             | 原生 `failed`；MCP 保留其真实结果                      | 诊断保留真实失败；MCP 足够时不强行警告           |
| MCP 失败                 | MCP `failed`；原生保留其真实结果                       | 抓取是否可用单独判断，不能由搜索失败推断抓取失败 |
| 两路均失败               | 两路 `failed`                                          | 如实说明无法完成当前核实                         |
| 预算不足以启动两条路线   | 至少一路 `attempted=false`                             | 说明本次限制；**不以单路结果冒充双路完成**       |
| 同一动作在同一修订内复用 | 复用必须指向真实观察与时间                             | 不算作新的联网执行                               |
| 查询被修改               | 形成**新的搜索动作**（新身份）                         | 与前一次动作分别记录                             |

单条路线的状态转换只有：从「未尝试」进入「已尝试」，并从「已尝试」收敛到 `succeeded` 或 `failed`。已收敛的状态不被后来的动作改写；新的动作使用新身份。`supported=true` 而 `attempted=false` 是**允许表达但不构成合规执行**的状态——它必须配合不足说明，不能被当作双路已完成。

## 不变量

1. **一旦执行新网页搜索，两条可用路线都真实执行**：支持原生且 MCP 可用时，不存在只开放两个工具、由模型自由决定调用哪一边的设计。
2. **不退回两路可选或一主一备**：两路实际执行是功能合同；时间上是否并行是执行策略。
3. **两路独立时默认并发，受约束时串行并记录实际时间**：串行不减少路线数，只改变时序。
4. **单路结果不冒充双路完成**：预算不足或一路不可用时，明确说明本次限制与不足。
5. **每路状态独立记录**：一路失败不撤销另一路的真实结果，也不把两路合并成一个成败。
6. **执行证据只接受可核实检索凭据**：供应商定义的实际搜索事件或能证明检索发生的结构化 grounding 元数据。
7. **相同 URL 不算两个独立信源**：两个渠道找到同一篇报道，不等于获得两个独立来源。
8. **复用指向真实观察**：同修订内成功的同一动作可复用，但必须指向真实观察与时间，不能算作新的联网执行。
9. **原生不支持时单 MCP 是正常配置**：不是降级，也不因此淘汰正常文本／MCP 路由。
10. **外发授权是前提**：双路不能绕过 `C04` 的开关与外发范围（`K09`）；数据边界优先于双路要求。

## 异常处理

| 失败分类                               | 反馈与可恢复性                                                         | 不得发生的行为                                                         |
| -------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 一条路线失败                           | 保留另一条真实结果，修复失败路线或按证据充足性继续；可恢复             | 因原生失败丢弃 MCP 结果，或因 MCP 失败丢弃原生结果                     |
| 原生返回只有生成文字、无可核实检索凭据 | 记录**协议／结果不足**；在预算内允许有依据的恢复                       | 伪造「原生已成功」；悄悄归成「模型不支持」（`Q17`／`G03`）             |
| 同一搜索动作恢复                       | 说明恢复过程与真实观察                                                 | 重复伪造新的「双路成功」                                               |
| 两路都失败或证据不足                   | 由 `C23` 返回缺口，`C14` 让模型继续行动（`K16`）                       | 隐藏限制；用摘要或模型生成的 URL 冒充检索结果                          |
| 空结果                                 | 如实保留，向模型反馈缺口，由模型修改关键词、时间或地区约束，或改查来源 | 把空结果当传输故障重复同一请求；让 Host 用关键词规则替模型编造查询语义 |
| 预算或授权在动作中途耗尽／撤回         | 停止该路线，说明限制；已取得的真实观察保留                             | 继续重试；以未授权路线补齐「双路」                                     |
| 配置在运行中变化                       | 由 `C20` 合成带配置版本的执行快照并保持可追踪                          | 由不同前端局部状态各自决定实际路线                                     |

失败与预期限制分开表达：原生不支持是**能力配置**，原生超时或失败是**运行故障**，二者诊断含义不同。

## 消费方

| 消费方 | 消费的字段                                               | 用途                                                                                                             |
| ------ | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `C20`  | 全部输入与输出字段                                       | 责任组件：冻结路线、申领资源、执行两路、合并候选与状态                                                           |
| `C10`  | `supported` 表达与能力状态的一致性                       | 提供可用路由与能力状态；维护 `unsupported`／`available`／`temporarily-failed`／`unknown`，不把临时失败写成不支持 |
| `C18`  | MCP 路线的 `attempted`／`succeeded`／`failed` 与传输结果 | 保持「连接健康、工具发现成功、业务结果有效」三件事分开                                                           |
| `C22`  | 候选来源、渠道来源标记、时间                             | 保存线索与来源身份；不把相同 URL 计为两个独立来源                                                                |
| `C25`  | 不足说明、两路真实状态                                   | 发布答案与必要限制说明；依据两者而不是模型自述                                                                   |

## 验证

本合同需要以下类别证据，判据定义在各 `V*` 对象中，本文件不新增判据：

- `V03`：请求身份、各路线状态字段的合法取值与互斥关系；相同 URL 的去重表达。
- `V04`：**生产入口**的两路执行、无原生时正常单路、一路失败保留另一路、取消与恢复；不得只用两个替身都被调用作为证据。
- `V05`：逐端点的原生搜索事件与 grounding 元数据（能否作为执行证据），以及 MCP 服务返回结构的可解析性。
- `V07`：分路状态、失败分类与不足说明在诊断中的可定位性（「两路只执行了一路」的直接检查交接为 `C10` → `C20` → `C12`／`C18`）。
- `V06`：双路对最终核实结果的语义贡献属于待验证问题，不是本合同的前置条件。

`V03` 机械负例已落在 `dual_path_search.rs`（注入双倍，不是生产入口两路）；`V04`–`V07` 当前仍为「未运行」或「待执行」（见 [evidence.md](../testing/evidence.md)）；`G02` 的阻断门槛为 `at=acceptance`。机械覆盖不是关闭。
