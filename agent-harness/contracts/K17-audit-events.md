# K17 审计事件与诊断查询

<!-- iris:object K17 kind=rules file=true -->

本文件是 `K17` 的正式定义位置，也是该合同唯一的正式定义位置。它约束**执行证据怎么被安全地记录、怎么被关联、怎么被解释**：事件关联字段、发现位置与归因状态的分离、错误码的语义、出站结构证据的边界、诊断呈现的三层结构，以及审计自身故障的表达。责任组件是 `C26`（安全边界事件），消费方是 `C26`、`C27`、`C11`、`C20`、`C21`。

本文件只定义审计事件与诊断查询，不复制相邻对象的正式定义：Run 生命周期与任务结果见 [K02](./K02-run-lifecycle.md)，工具面版本与派发状态见 [K10](./K10-tool-surface.md)，额度与分类计数见 [K06](./K06-budget-ledger.md)，协议终止原因与续轮保真见 [K04](./K04-provider-capability.md)，两路搜索状态见 [K11](./K11-dual-path-search.md)，抓取与正文完整性见 [K13](./K13-web-reading-window.md)，恢复与停止原因见 [K16](./K16-verification-report.md)，来源身份见 [K14](./K14-evidence-and-provenance.md)。

本文件的编译依据是架构定义的错误归属一节（发现位置、故障来源、影响与归因状态；程序／服务／模型行为的分类；三层诊断呈现；审计自身故障）与讨论纪要第十四节（现有记录能看到动作未必能还原因果；出站结构证据的作用与边界）。`implementation.state` 只描述源码事实，不代表合同正确或用户任务可用；C26 已接入出站结构见证与完整循环事件的记录路径，但诊断查询视图、已知故障演练与工具名来源区分仍属缺口（`G04` 未关闭），诊断关联不完整（`Q09`）、缺少可呈现的出站结构诊断（`Q18`）、未知工具名来源无法区分（`Q01`、`Q12`）按 `Q*` 引用，不在此宣称已解决。

## 接口

**输入**（设计层逻辑类型，不是已存在的 Rust 类型或 IPC 字段）：

| 输入         | 含义                                                             | 权威所有者                                       |
| ------------ | ---------------------------------------------------------------- | ------------------------------------------------ |
| 各模块事件   | 模块、组件、工具与模型行为的开始、结束、失败与恢复事实           | 各业务组件对自己的执行事实负责                   |
| 调用身份     | Run、输入修订、父／子任务、模型回合、调用与尝试 ID               | `C02`／`C03`／`C15`／`C12`；工具面版本来自 `C16` |
| 边界关联标识 | 上下文进入网关前后、请求发出与返回等交接的关联标识               | `C07`／`C11`；出站结构由 `C11` 提供              |
| 结构见证     | 出站消息角色与数量、必要字段是否存在、修复消息是否纳入、所用协议 | `C11`（`K04`）                                   |
| 权威状态     | Run 生命周期、派发观察、额度累计与验证结果                       | `C02`、`C17`、`C13`、`C23`                       |
| 查询请求     | Run／调用 ID 及下钻范围                                          | `C27`／诊断入口                                  |

**输出**：

1. **可关联记录**：追加式事件与其关联字段；每条记录标明发现位置（哪个模块、组件、工具实例或模型调用），且记录不保存参数或原始输出。
2. **持久化状态**：写入成功、失败、缺口或未知；事件不完整时必须给出缺口类型。
3. **诊断查询结果**：已知事实、直接失败、恢复结果与待证根因，按三层呈现——首屏摘要（一句话指出主要失败点、实际影响、恢复状态与归因确定性）、执行路径（模块 → 组件 → 调用实例下钻）、依据详情（安全错误码、时间与耗时、尝试次数、资源计数、前后交接状态、关联事件与缺失证据）。
4. **缺口报告**：缺开始／结束事件、关联断裂、持久化失败或进程中断后结果未知。

**事件关联字段**（每条相关记录都必须能回答「哪个会话、Run、输入修订、父／子任务、模型回合、调用与尝试，使用了哪个工具面与协议适配版本」）。**分离表达的四个属性**：发现位置、已证实的故障来源、关联影响、归因状态——四者不得压成一个字段，也不得用一个「首错」概括整个 Run。

**安全边界**：不记录密钥、笔记正文、完整模型请求或私有推理；模型返回的错误字符串、未知工具名与 URL 需脱敏后才能进入记录；诊断数据默认仅用于本地内部查看，不自动上传，日志与诊断导出同样遵守该边界。

**边界**：`C26` 不保存第二套运行状态，不通过 AI 猜测代替事实，不控制业务执行；`C27` 只读取 `C26` 的事件与权威状态作出解释，不改写它们。

## 状态转换

事件本身是**追加式**记录：已经写入的失败不被后续成功覆盖，已写入的记录不因任务结果改变而被就地改写。

归因状态取以下离散值，且只允许按「证据增加」的方向转换：

| 归因状态          | 含义                                             | 允许的去向                                              |
| ----------------- | ------------------------------------------------ | ------------------------------------------------------- |
| `unattributed`    | 尚无法归因                                       | `suspected`、`confirmed`、`multiple-causes`；或保持未知 |
| `suspected`       | 疑似某个来源，证据不足                           | `confirmed`、`unattributed`、`multiple-causes`          |
| `confirmed`       | 已证实的具体故障来源（限定在该边界可证明的范围） | 保持；新证据可追加记录，不覆盖旧结论                    |
| `multiple-causes` | 存在多个独立原因                                 | 保持；可拆分记录，不强行合并                            |

记录完整性取以下离散值：`complete`、`missing-events`、`broken-correlation`、`persist-failed`、`outcome-unknown`（进程中断后结果未知）。诊断呈现的三层是**视图层级**，不是状态机；下钻不改变底层记录。

恢复结果（失败、反馈、修正提议、重试、恢复）作为关联记录保留；`recovery_exhausted` 一类结果是恢复结果，不是根因，不得写入归因字段冒充 `confirmed`。

## 不变量

1. **发现位置与故障来源分离**：某组件拒绝了一个提议，只说明错误在该边界被发现，不说明该组件有缺陷；错误码、发现组件与根因不是同一个字段。
2. **不强行压缩成单一首错**：一个 Run 可以有多个独立问题；时间上先出现的错误不自动成为全部后续错误的根因，依赖关系与明确传播关系才用于关联因果。
3. **恢复结果不是根因**：恢复耗尽、重试次数用尽是恢复结果；诊断不得把它们当作根因，也不得把「缺事件」默认成执行成功。
4. **正常限制独立展示**：用户取消、正常权限拒绝、能力不支持、额度耗尽属预期限制与控制结果，独立展示；只有限制配置或执行违反合同才归入内部错误。
5. **不记录敏感内容**：密钥、笔记正文、完整模型请求与私有推理不进入事件、审计、导出或诊断日志；模型返回的错误字符串、未知工具名与 URL 先脱敏再记录。
6. **出站结构证据只证明传递**：消息角色与数量、必要字段是否存在、修复消息是否被纳入、所用协议与边界关联标识能证明必要信息的传递与关联，**不能证明语义理解**；不得据此断言模型已理解反馈。
7. **区分四个层级的事实**：业务层生成了反馈、网关序列化了反馈、请求已发送、供应商返回了什么，分别记录；前一事实不能冒充后一事实。
8. **审计自身故障独立呈现**：审计写入失败必须通过独立的运行内健康状态或 UI 信号表达，不能要求仅靠同一个已失效的日志通道报告自身失败；诊断查询失败不得伪装成「没有发现错误」。
9. **机械与语义分列**：机械可证的违规与语义判断分开展示；语义评估保留判据、来源与不确定性，支持授权人工复核，不输出未经校准的责任概率。
10. **清理后如实说明**：记录保留、清理与导出遵循独立权限与容量边界；清理后明确哪些历史运行已不可完整诊断，历史状态不因清理被改写为成功。

## 异常处理

| 失败分类                   | 反馈对象与可恢复性                                                                                  | 不得发生的行为                               |
| -------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 事件缺失或关联断裂         | 标记 `missing-events`／`broken-correlation` 并反馈给 `C27` 与相关组件；可恢复（补齐关联后追加记录） | 默认执行成功；把所有相关模块标成失败         |
| 终止事件未写入（进程中断） | 由持久状态与缺口规则标识中断或结果未知（`outcome-unknown`）；可恢复（读取安全快照与已有事件）       | 自动重试结果未知的非幂等副作用；声称结果已知 |
| 审计写入失败               | 通过独立的运行内健康状态或 UI 信号呈现，并记录可诊断性缺口；不阻断已经取得的正确答案                | 仅用同一条日志通道报告自身失败；静默丢弃记录 |
| 诊断查询失败               | 明示查询失败及其范围                                                                                | 返回空结果冒充「没有发现错误」               |
| 归因证据不足               | 标为 `suspected`／`unattributed`，说明尚缺什么；可恢复（补事件或受控复现）                          | 输出未经校准的模型责任概率；以模型名称定罪   |
| 发现敏感内容已进入记录     | 按最小化与脱敏约束处理并记录处理事实                                                                | 把原文复制进日志、导出或评测报告             |
| 历史记录已清理或不可重取   | 明确标出不可完整诊断的范围                                                                          | 用推断补写缺失事件冒充原始记录               |
| 故障类型本身需要验证       | 由已知故障注入检查诊断是否指向正确层级（`V07` 的故障类型清单）                                      | 以日志行数或事件数量作为「审计可用」的依据   |

诊断入口的信息与交互合同：必须能直接从对应回答或失败提示进入并自动关联本次 Run，无需用户先复制 ID 或检索日志；状态同时使用文字与符号，不只依赖颜色；「本组件失败」与「受上游失败影响未执行」分开呈现；已恢复的问题仍可查看，成功答案不因一次已恢复的超时被整体标红。

| `C27`  | Run／调用 ID、关联字段、权威状态、缺口类型 | 查询与解释：给出已知事实、直接失败、恢复结果与待证根因；缺事件必须报告缺口，不把恢复耗尽当根因                           |

| `C20`  | 两路路线的执行证据、分路状态与不足说明     | 记录每次获准搜索的真实执行证据：以供应商定义的实际搜索事件或可证明检索发生的结构化元数据为准；缺凭据时记录协议／结果不足 |

## 验证

本合同需要的证据类别定义在各 `V*` 对象中，本文件不新增判据：

| 判据  | 适用于本合同的内容                                                                                                                                                   |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `V03` | 局部机械不变量：关联字段是否存在、四类属性是否分字段、脱敏规则、归因状态与记录完整性取值合法                                                                         |
| `V04` | 跨组件与生产入口：Run → 输入修订 → 模型回合 → 尝试 → 工具调用 → 父子任务的关联；出站结构见证与真实请求的一致性                                                       |
| `V05` | 部分适用：协议事件、终止原因与原生搜索事件的接入需要逐端点证据（`Q04`、`Q10`、`Q17`）；该证据证明协议事实被保真记录，不证明语义理解                                  |
| `V06` | 部分适用：涉及模型行为与答案质量的语义归因需要真实模型样例与人工抽检；自动评价只作辅助，不得替代人工复核                                                             |
| `V07` | 主判据：诊断界面与交互、状态投影与「已知故障能定位」；故障类型至少覆盖内部合同错误、外部失败、正常拒绝、失败后恢复、多路部分成功、多故障并存、事件缺失与审计存储故障 |
| `V08` | 记录绑定：诊断与验证证据须绑定对象指纹、测试或检查清单路径、复现命令、环境与执行时间；指纹变化后原记录降为 `needs-review`                                            |

`V03`–`V07` 当前状态一律为「未运行」或「待执行」（见 [acceptance-matrix.md](../testing/acceptance-matrix.md)）；引用它们不表示本合同已通过验收。「审计可用」的必要结果是已知故障能定位、传播关系能解释、恢复不会抹去原始失败、证据缺口能看见、正常限制不会被误报为 bug，不能只以日志行数或事件数量作为完成依据。
