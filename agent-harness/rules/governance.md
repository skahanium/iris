# 治理规则：权威、状态、变更、复核与阻断

<!-- iris:object P03 kind=rules file=true -->

本文件固定 Agent Harness 文档体系的**权威边界、状态语义、关系模型、变更分类、复核要求、历史适用性与阻断规则**。它不重复对象身份与标记规则（见 [objects.md](./objects.md)），也不规定任何模块、组件、工具的技术内容——那些在各对象的正式定义里。

## 一、权威边界

### 1.1 四层材料的职责

| 材料                                                                     | 角色                   | 本体系如何使用它                                                |
| ------------------------------------------------------------------------ | ---------------------- | --------------------------------------------------------------- |
| [讨论纪要](../../AGENT-REFORM-DISCUSSION-2026-09-14.md)                  | 解释来源与事实边界     | 作为 `SRC-DISC-2026-09-14` 来源对象绑定版本；不作为规范条文     |
| [Agent 架构定义](../../docs/agent-architecture.md)                       | 上位决定（架构权威）   | 作为 `SRC-ARCH-2026-09-15` 来源对象；模块/组件/工具身份由它派生 |
| 本体系（`agent-harness/`）                                               | 详细规范与施工依据     | 对象正式定义的唯一位置；施工记录、证据要求与工作包状态在此      |
| [ARCHITECTURE.md](../../ARCHITECTURE.md)、[ROADMAP.md](../../ROADMAP.md) | 当前实现事实与版本排期 | 实现事实以上位现有文档为准；**版本排期唯一来源仍是 ROADMAP**    |

本体系**不承担**版本排期、不自动证明合同合理或工具可用、不替代真实模型验收、不读取模型私有思维链。

### 1.2 归档不得作为依据

`agent-harness/archive/` 与 `docs/archive/` 只作对照。现行文档不得把归档材料作为规范性依据，也不得引用其阶段完成度。归档入口只经 [docs/README.md](../../docs/README.md) 与本体系 [README](../README.md) 的归档段进入。

### 1.3 一个对象只有一个正式定义

对象定义分散会导致两处authority。因此：

- 每个对象的正式定义正文只写在登记表指定的一个文件里；
- 其他位置只允许引用（相对链接或反引号 ID），不允许再写一遍定义；
- 链路文档（`L*`）说明交接顺序并引用合同（`K*`），**不重复定义合同**；
- 模块文档（`M*`）说明模块责任与状态权威，组件合同（`C*`）写在所属模块文件内，工具卡（`T*`）只写工具自身合同并引用它消费的合同 ID。

## 二、状态维度

状态分为**四个独立维度**，不允许压成一个“完成度”标签。

### 2.1 文档成熟度（`definition.maturity`）

| 值           | 含义                                                                                   | 允许依据                 |
| ------------ | -------------------------------------------------------------------------------------- | ------------------------ |
| `registered` | 只有登记：稳定 ID、种类、责任归属、摘要、明确缺口                                      | 可以作为待补齐关系的目标 |
| `draft`      | 已有正式定义正文，仍在修订                                                             | 不能支持施工依赖         |
| `defined`    | 正式定义完整：输入输出、决定权、状态、不变量、异常、审计、源码落点、兼容、测试九项齐备 | 可被引用为规范           |
| `superseded` | 已被替代对象取代                                                                       | 消费者必须迁移           |
| `retired`    | 退役，保留身份                                                                         | 只作历史读取             |

`registered` 的条目 `definition` 必须为 `null`；`draft` 及以上必须有真实标记与指纹。已声明定义却找不到标记是错误，不能退回 `registered` 绕过检查。

### 2.2 实现状态（`implementation.state`）

`absent` / `partial` / `present` / `unknown`。这一维度只描述**源码事实**，不描述质量：`present` 不等于合同正确，也不等于用户任务可用。

### 2.3 验证结果（`verification.state`）

`none` / `partial` / `passed` / `failed` / `stale`。`stale` 表示证据存在但绑定的是旧内容指纹，当前版本不再适用。

### 2.4 工作包状态（`work.state`）

`planned` / `ready` / `active` / `blocked` / `done` / `cancelled`。

### 2.5 当前适用性由计算得出

`effective` 状态（可施工性、可验收性）**不读历史标签，只按当前有效性与依赖计算**：

```text
可施工(work) = work.state ∈ {planned, ready}
             ∧ 全部 depends_on 前置的 definition.maturity = defined
             ∧ 全部 depends_on 前置的 effective 就绪成立
             ∧ 不存在 state=open 且 at=start 的 blocks 边
             ∧ 作用域内没有改变实现的未决问题（Q* 中 scope 命中且 state=open）

可验收(object) = definition.maturity = defined
             ∧ 该对象需要维度的必需证据齐备且未 stale
             ∧ 不存在 state=open 且 at=acceptance 的 blocks 边
             ∧ 全部 upstream 复核已解封
```

历史测试通过不可改写为失败；历史验收也不删除。但历史通过不足以支持变化后的当前验收——变化后必须重新计算。

## 三、关系模型

### 3.1 边类型与方向

关系多对多，不采用单一父节点。只有 `depends_on` 与 `supersedes` 要求无环。

| 边           | 固定方向                  | 变化后的处理                                       |
| ------------ | ------------------------- | -------------------------------------------------- |
| `implements` | 实现对象 → 要求／合同     | 要求或合同定义变化时，沿入边查找实现对象，进入复核 |
| `consumes`   | 消费者 → 被消费对象       | 被消费定义变化时，沿入边查找消费者，进入复核       |
| `verifies`   | 测试 → 被验证声明／不变量 | 被验证定义变化时，测试设计与关联证据适用性进入复核 |
| `depends_on` | 依赖者 → 前置对象         | 前置状态变化时，沿入边重新计算依赖者的就绪状态     |
| `blocks`     | 问题 → 工作包／验收声明   | 问题状态变化时，沿出边重新计算指定门槛             |
| `supersedes` | 新对象 → 旧对象           | 从旧对象的消费者关系启动迁移检查；**禁止自动改指** |
| `refs`       | 来源对象 → 被其确立的对象 | 来源指纹变化时，沿出边把对象置入复核               |

### 3.2 `blocks` 必须注明门槛

`blocks.at` 只取 `start` 或 `acceptance`。某缺陷通常阻止验收，不应因此阻止修复它的工作包开始——把 `at` 写错会直接改变就绪计算。

### 3.3 问题关闭不等于解封

关闭一个问题只移除**该问题造成的**阻断。其他问题、过期合同、缺失证据或未完成前置仍然有效；不会自动把工作包提升为可施工或已验收。

## 四、变更分类

### 4.1 架构变更 vs 细化

| 变化内容                                                                       | 分类     |
| ------------------------------------------------------------------------------ | -------- |
| 责任归属、状态权威、输入输出语义、决定权、不变量、权限、副作用、兼容、用户承诺 | 架构变更 |
| 字段落实、内部实现、示例、说明文字、排版（上述承诺不变）                       | 细化     |

- 新增字段、调整默认值或超时**不能自动**被视为细化。
- 检查器规则、复核权限、验收门槛自身的变化属于**治理变更**，按架构变更复核。
- 检查器**不声称能机械判断语义是否等价**：它要求变更记录给出分类与理由，由复核确认。

### 4.2 变更记录

每次接受变化写入 `registry.json.changes[]`：

| 字段             | 含义                                         |
| ---------------- | -------------------------------------------- |
| `id`             | 变更 ID（`CHG-<日期>-<序号>`）               |
| `objects`        | 涉及对象及其修订前后修订号与指纹             |
| `classification` | `architecture` / `refinement` / `governance` |
| `reason`         | 分类理由（必填）                             |
| `author`         | 变更作者                                     |
| `review`         | 复核记录 ID；架构变更在解封前必须存在        |

## 五、传播与复核

### 5.1 两类事件

| 事件                     | 处理                                       |
| ------------------------ | ------------------------------------------ |
| 定义或实现变化           | 按关系类型产生复核与重新验证要求           |
| 问题、前置或复核状态变化 | 重新计算就绪与阻断，**不**自动判定定义失效 |

传播用工作队列去重处理，保留每项影响的**原因路径**（如 `C20 → consumes → K12 → 指纹变化`）。上游影响未解决时，下游不能通过局部确认提前恢复有效状态。

### 5.2 独立复核

**架构变更后的“无影响”结论必须由独立 AI 或人工复核。**

复核记录（`registry.json.reviews[]`）必须绑定：

- 变更 ID、对象 ID、变更前后修订与内容指纹；
- 具体差异范围、受影响对象、判断理由；
- 变更作者、复核者、可追溯评审记录（外部材料路径或 `docs/eval/results/` 证据 ID）。记录字段语义固定为：`changes[].author` 是变更作者，`reviews[].author` 是复核者，`reviews[].reviewer` 是参与该变更编写的身份（用于核对独立性）；
- 处理结论：`no-impact` / `synchronized` / `needs-reverification` / `superseded`。

判定规则：

1. 架构变更的作者**不能**自行作出无影响结论解除阻断。
2. “独立 AI”指未参与该变更编写的评审任务；**不同署名或模型名称本身不构成独立性证据**——检查器只核验记录完整性、身份区别、关联版本与评审记录是否存在，不把字符串比较宣称为身份认证。
3. 纯细化允许作者自审，但必须引用具体差异与理由。
4. 改变行为或验证判据时，无论由谁复核，都必须补充相应验证，**不能用“无影响”代替测试**。
5. 复核绑定旧差异、缺少理由，或复核之后对象又变化，都不能解封。

## 六、历史与当前适用性

- 保留文档成熟度、实现状态、验证结果、工作包状态四个维度，互不覆盖。
- 替代关系保留旧身份与旧版本。当前消费者必须显式迁移；历史记录可继续绑定旧版本，但**不能据此宣称新版本已验证**。
- 证据通过 `applicability` 标注 `current` / `needs-review` / `obsolete`；`obsolete` 不计入必需维度。

## 七、归档

1. 退役材料整批移入 `agent-harness/archive/<日期>-<原因>/`，并写 `MANIFEST.md`。
2. `MANIFEST.md` 必须登记该目录下每个文件（含来源路径、归档原因、有效内容去向）。
3. 新增归档文件必须在对应 `MANIFEST.md` 登记；`npm run docs:check` 强制校验登记完整性与引用方向。
4. 归档不继承状态、不批量抹去历史状态：旧体系的有效任务逐项迁移并标注去向。

## 八、检查器与阻断

本体系的机械检查入口是 `scripts/agent-harness-check.mjs`（`X01`），其负例自测是
`scripts/agent-harness-check.test.mjs`（`X02`）。它们只执行本文件与 [objects.md](./objects.md)
写明的规则，不做语义判断，也不静默修改文档或历史记录。

### P03 正式定义

## 治理对象要点

- **权威边界**：四层材料各司其职（讨论纪要、架构定义、本体系、既有实现文档）；归档只作对照。
- **状态四维**：文档成熟度、实现状态、验证结果、工作包状态互不覆盖；`effective` 由计算得出。
- **关系模型**：`implements`／`consumes`／`verifies`／`depends_on`／`blocks`／`supersedes`／`refs` 方向固定；`depends_on` 与 `supersedes` 无环。
- **变更分类**：架构变更与细化的分界写在正文；变更必须给出分类与理由，检查器不做语义判断。
- **独立复核**：架构变更的「无影响」结论不能由作者自签；复核必须绑定当次指纹。
- **阻断纪律**：结构违规退出码 1，执行基础设施失败退出码 2，两者都不允许兜底放行。

## 不变量

1. 一个对象只有一个正式定义位置。
2. 未解决的上游影响不能被局部确认提前解封。
3. 问题关闭只移除该问题造成的阻断，不提升其他门槛。
4. 历史通过保留，但不支持变化后的当前验收。

### X01 文档体系检查器

`scripts/agent-harness-check.mjs` 是本体系的唯一机械检查入口。它只执行 [objects.md](./objects.md) 与 `P03` §9 写明的规则，**不做语义判断**，也不静默修改文档或历史记录。

| 组     | 检查项                                                                            |
| ------ | --------------------------------------------------------------------------------- |
| 身份   | ID 前缀与 kind 一致、无重复 ID、无未登记对象标记                                  |
| 结构   | 每份托管文件有且只有一个文件级对象、标记成对不嵌套、无无法归属的正文              |
| 登记   | `registry.json.files` 与磁盘一致、声明 `defined` 的对象必须有真实定义位置         |
| 指纹   | 对象指纹、文件级指纹与来源指纹同登记一致（未接受的变化报错）                      |
| 关系   | 边端点存在、`depends_on`/`supersedes` 无环、`blocks` 注明门槛、`scope` 有需求依据 |
| 成熟度 | 声明 `defined` 的对象必须写全该种类必备合同要素                                   |
| 就绪   | 可施工与可验收按依赖、阻断、证据的当前有效性计算，不读历史标签                    |
| 复核   | 架构/治理变更必须有独立复核；复核绑定旧差异时不能解封                             |
| 证据   | 声明 `verification.state=passed` 必须有 verify 记录且指纹未过期                   |
| 归档   | 归档目录必须有 `MANIFEST.md`，登记完整且反向可达                                  |
| 索引   | `docs/README.md` 必须登记 `agent-harness/README.md` 作为现行入口                  |

退出码：`0` 全部检查完整执行且通过；`1` 结构或规范违规；`2` 执行基础设施失败（注册表不可解析、文件无法读取、脚本异常）——**不等于“发现规范问题”**。

### X02 检查器负例自测

`scripts/agent-harness-check.test.mjs` 用 `node --test` 运行，夹具全部在系统临时目录生成，**不写入仓库**。它覆盖 `document.md` §5 的检查器测试清单：多消费者共享合同、各边类型的变化与传播方向、一个问题关闭而另一阻断仍在、只有登记的对象不能支持可施工声明、定义缺失与标记损坏与对象移动、无关对象保持有效、作者自签不能解封而独立复核可以、复核绑定旧差异不能解封、历史通过不足支持当前验收、缺少反例或空分母不能通过验收、注册表损坏与文件读取失败均返回失败。

首批成功标准：**全局对象登记完整，正式定义与草案可以区分，变化能够传播，解封具有依据，检查失败不会放行，D0 能交给另一位工程师直接施工。**

### X03 登记表

`agent-harness/registry.json` 是登记表的权威存储：身份、正式定义位置与行号、修订、内容指纹、类型化关系、来源指纹、证据记录、变更与复核记录、问题状态。它由 `catalog.mjs`（人工维护的身份与关系）加 `agent-harness-check.mjs --reconcile`（计算得出的指纹与修订）共同产出。

**规则**：

- 登记表自身的文件级标记是首行 `<!-- iris:object FILE-REGISTRY kind=rules file=true -->`（JSON 不能承载注释）；
- 指纹、修订与行号是计算值，禁止手写；
- 接受变化必须给出作者、分类与理由，并留下 `changes` 记录；架构与治理变更还需要独立复核（`reviews`）；
- 登记表不可解析、与实际内容不一致或缺少必需段，一律阻断检查，不降级为警告。
