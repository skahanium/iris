# M9 审计与诊断

<!-- iris:object M09 kind=rules file=true -->

**唯一主要责任**：独立负责执行证据的可解释性，业务模块提供安全事件。它不保存第二套运行状态，不通过 AI 猜测代替事实。本模块承担架构 §3 M9 的「用户补充要求（2026-09-15）」诊断定位合同。

**状态权威与禁止行为**：本模块拥有「边界关联与诊断缺口」逻辑对象。主要读取者是诊断 UI、评测。禁止行为：哈希存在就声称信息完整。对应登记为 [架构定义](../../docs/agent-architecture.md) §4 状态所有权表第十行。

**用户补充要求（2026-09-15）**：内部错误审计必须覆盖模块、组件、工具和模型行为，并提供清晰直观的定位。诊断入口应让人一眼看到哪里出现了什么问题、影响了什么、是否恢复及判断依据，而不是只能翻日志猜测。此要求属于目标架构的必要能力。`C26` 负责事件覆盖、关联与记录完整性，`C27` 负责故障归因、诊断摘要和可下钻视图；各业务组件仍对自己的执行事实负责。模型行为纳入诊断对象，**不因此新增第十个运行时模块**（§3 M9）。

## 输入与输出

**输入**：

- 各模块事件、调用身份与结构见证（`C26`）。
- Run／调用 ID、`C26` 事件与权威状态（`C27`）。
- 来自 `M01` 的运行与修订身份、来自 `M04` 的出站结构、来自 `M06` 的派发观察、来自 `M05` 的恢复轨迹、来自 `M08` 的交付结果。

**输出**：

- 可关联记录及持久化状态（`C26`）。
- 已知事实、直接失败、恢复结果、待证根因（`C27`）。

## 决定权

- 决定事件覆盖、关联与记录完整性的表达（`C26`）。
- 决定故障归因、诊断摘要与可下钻视图的呈现（`C27`）。
- 不控制业务执行，不保存第二套运行状态，不通过 AI 猜测代替事实，不新建让 AI 猜根因的审计 agent（§3 M9、讨论十四）。
- 只把机械断点定位清楚：材料相关性、推荐偏好和复杂事实争议仍需语义评价，**不能承诺每次都自动得到唯一根因**（§8.5）。

诊断定位的四项信息（§8.1）：

| 信息           | 必须能回答的问题                                                                            |
| -------------- | ------------------------------------------------------------------------------------------- |
| 运行与版本身份 | 哪个会话、Run、输入修订、父／子任务、模型回合、调用与尝试？使用了哪个工具面与协议适配版本？ |
| 定位对象       | 哪个 `M` 模块、`C` 组件、工具实例、MCP 服务或模型调用？内部工具名与外部服务别名分别标识     |
| 失败事实       | 哪个阶段违反了什么合同，预期和实际状态是什么？使用稳定错误码及易懂说明                      |
| 归因状态       | 已证实、疑似、无法归因，还是存在多个独立原因？证据指向何处，尚缺什么？                      |
| 影响与恢复     | 是局部失败、阻断后续、结果不完整还是没有影响最终交付？重试、改查、回退是否成功？            |
| 记录完整性     | 是否缺开始／结束事件、关联断裂、持久化失败，或进程中断后结果未知？                          |

错误码、发现组件和根因**不是同一个字段**。依赖关系与明确传播关系用于关联因果；时间上先出现的错误不能自动成为全部后续错误的根因。一个 Run 可以有多个独立问题，诊断摘要不能强行压成一个「首错」（§8.1）。

## 状态

| 状态项   | 内容                                             | 边界                              |
| -------- | ------------------------------------------------ | --------------------------------- |
| 边界事件 | 各模块的交接事件、关联标识、记录完整性标记       | 只由 `C26` 记录                   |
| 诊断缺口 | 缺事件、关联断裂、持久化失败、结果未知           | 只由 `C26` 标识并交 `C27` 呈现    |
| 归因结论 | 已证实／疑似／无法归因／多个独立原因，及尚缺证据 | 只由 `C27` 表达，必须绑定事实依据 |

本模块**不保存第二套运行状态**：权威状态仍归各业务模块（§4）。必要授权或变更回执无法持久化时不执行新的持久副作用；可选诊断写入失败则记录可诊断性缺口，不自动抹掉已经取得的正确答案（§3 M9）。

## 不变量

1. 哈希存在不能声称信息完整（§4 禁止行为）。
2. 只有哈希不足以解释字段缺失；需要安全的结构证据，如消息角色与数量、必要字段是否存在、修复消息是否被纳入、所用协议，以及前后边界的关联标识（§8.4）。
3. 不记录密钥、笔记正文或私有推理；失败、重试、父子关系和修订号必须可关联（§3 `C26`）。
4. 不把恢复耗尽当根因；缺事件必须报告缺口，**不能默认执行成功**（§3 `C27`）。
5. 重要交接须有开始、终止或明确未知状态；每次失败和恢复保留因果关联，不能只记最后一次成功（§8.4）。
6. 进程崩溃来不及写终止事件时，由持久状态与缺口规则标识中断或结果未知，**尤其不能自动重试未知副作用**（§8.4）。
7. 诊断数据默认仅用于本地内部查看，不自动上传（§8.4）。
8. 已有授权会话、候选与来源可通过受控引用在本地详情中按需核验，不复制进诊断日志；材料已删除或授权已撤回时如实说明不可核验（§8.4）。
9. 审计读取不得写入配置或业务状态：查询保持只读。`Q05` 指出的读取时修复并写库是当前缺陷。
10. 审计失败与任务失败分别表达（§3 M9）。

## 异常与恢复

- 审计写入失败：必须通过**独立的运行内健康状态或 UI 信号**呈现，不能要求仅靠同一个已失效的日志通道报告自身失败（§8.4）。
- 诊断查询失败：不能伪装成「没有发现错误」（§8.4）。
- 记录保留、清理及导出遵循独立权限与容量边界；清理后明确哪些历史运行已不可完整诊断（§8.4）。
- 缺开始／结束事件：标为记录不完整或结果未知，不推断成功。
- 模型返回的错误字符串、未知工具名和 URL 需脱敏，**不能直接当作安全文本记录**（§8.4）。

## 审计

本模块的审计行为即其产品能力，具体呈现合同（§8.3）：

1. **首屏摘要**：用一句话指出主要失败点、实际影响和恢复状态，同时显示归因是否确定及诊断是否完整。已恢复的问题仍可查看，成功答案不因一次已恢复超时而被整体标红。
2. **执行路径**：按模块 → 组件 → 调用实例下钻，展示正常、运行中、失败、部分成功、已恢复、受阻、未执行及未知状态。父子任务、原生／MCP 两路和重试分支分别可见；状态同时使用文字和符号，**不能只依赖颜色**。
3. **依据详情**：查看安全错误码、时间与耗时、尝试次数、资源计数、前后交接状态、关联事件及缺失证据。将「本组件失败」和「受上游失败影响未执行」分开，避免整个后续路径都被误认成有 bug。

诊断视图必须直接从对应回答或失败提示进入，自动关联本次 Run，**无需用户先复制 ID 或检索日志**（§8.3）。具体布局沿现有设计系统实现。

以下仅为目标呈现示例，**不是已有运行结果**（§8.3）：

> 局部失败，答案已交付。`M07` 检索与证据 → `C21` 网页读取 → `web_fetch`，第 2 个页面正文提取失败；另 2 页可用，后续核验采用其内容。已确定：读取结果不满足正文合同。待确认：站点限制还是提取服务问题。

分类必须区分程序、服务与模型行为（§8.2）：

| 类别                   | 典型情形                                                   | 归因边界                                                             |
| ---------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| 内部实现或合同错误     | 上下文漏装、续轮字段丢失、状态投影错误、工具面版本不一致   | 定位责任组件及违反的合同，不统称模型能力不足                         |
| 外部服务或传输错误     | 超时、限流、鉴权失败、MCP 断连、供应商返回协议不符         | 保留具体服务与请求身份；鉴权失败还需排查配置，不能直接认定供应商故障 |
| 工具执行或结果错误     | 参数无效、派发失败、部分写入、抓取只有空正文               | 传输成功、工具执行成功、结果可用分别判断；参数错误的产生位置另查     |
| 模型行为与答案质量问题 | 提议未知工具、未遵守已送达约束、结论不受材料支持、回答偏题 | 记录具体可观察行为和核验依据，不以模型名称或另一模型一句评价定罪     |
| 预期限制与控制结果     | 用户取消、正常权限拒绝、能力不支持、额度耗尽               | 独立展示，不一律算程序错误                                           |
| 诊断不足               | 事件缺失、资料不可重取、无法确认字段是否送达               | 明确标为未知或待证，不默认成功，也不把所有模块标成失败               |

## 兼容

- 历史 Run 的事件回放与审计记录保留可读；`assistant_run_get` 回放仅恢复安全快照与过程展示，不重新执行模型或工具。
- 涉密 Run 仅在当前进程内易失执行，`assistant_run_get` 仅可在同一进程内按显式 run ID 读取无正文的易失快照与安全事件，不支持省略 run ID 的活动 Run 查询、持久化断流回放或进程级恢复（[ARCHITECTURE.md](../../ARCHITECTURE.md)）。
- 记录清理后必须明确哪些历史运行已不可完整诊断，不能把「查不到」当作「没问题」（§8.4）。
- 旧日志只有成功却无法解释行为时，缺失关联或缺失事件明确标为诊断不足（§8.5）。

| 需求／判据                                          | 覆盖方式                                                                                                         |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 内部错误审计覆盖模块、组件、工具与模型行为（`N18`） | 已知故障检查诊断指向正确层级（§8.6、`V07`）                                                                      |

故障类型至少包括：内部合同错误、外部失败、正常拒绝、失败后恢复、多路部分成功、多故障并存、事件缺失及审计存储故障。每个案例同时检查定位对象、错误分类、归因状态、恢复与影响表达、关联路径及敏感信息隔离；模型质量问题还要检查是否把推断错误地显示成已证实根因（§8.6）。

测试替身与故障注入用于检验机械归属，真实模型样例与人工抽检用于校准语义判断；**二者不能互相冒充**（§8.6）。**不能只以日志行数或事件数量作为完成依据**（§8.6）。本模块 `M09`、`C26`、`C27` 当前 `implementation.state=partial`，全部 `verification.state=none`。

### M09 正式定义

## 模块级合同要点

- **唯一主要责任**：独立负责执行证据的可解释性；业务模块提供安全事件。
- **状态权威**：边界关联与诊断缺口由本模块独占；不保存第二套运行状态。
- **禁止行为**：把恢复耗尽当根因；缺事件时默认执行成功；在日志中记录密钥、笔记正文或私有推理。
- **定位维度**：发现位置、已证实故障来源、关联影响、归因状态四者分离（`K17`）。
- **依赖**：事件由各模块边界提供，出站结构证据来自 `C11`，分路状态来自 `C20`／`C21`。

## 组件边界

`C26` 负责事件覆盖、关联与记录完整性；`C27` 负责故障归因、诊断摘要与下钻视图。审计写入失败必须独立呈现。

### C26 安全边界事件

## 输入与输出

- **输入**：各模块事件、调用身份与结构见证。
- **输出**：可关联记录及持久化状态。
- **逻辑合同名称**：设计层名称，不是已存在的 Rust 类型或 IPC 字段；所属模块 `M09`。

## 决定权与不变量

- **决定权**：不记录密钥、笔记正文或私有推理；失败、重试、父子关系和修订号可关联。
- **不变量**：重要交接有开始、终止或明确未知状态；出站结构见证只证明传递不证明理解。
- **禁止行为**：越权改写其他模块的权威状态；把提议当作执行；把缺失当作成功。

## 状态

本组件持有的状态与其权威范围见上；持久状态只有 `M09` 的权威所有者可写，其余为进程内观察。

## 异常与恢复

审计写入失败通过独立健康状态呈现；不因日志失败掩盖任务结果。失败分类使用稳定错误码，可恢复的错误按 `K16` 反馈后继续。

## 审计

事件覆盖、关联键（Run／修订／父调用／尝试／工具面版本）与缺口进入诊断。不记录密钥、笔记正文、完整模型请求或私有推理。

## 源码落点

现有基础与处置：`boundary_events.rs` 为 C26 追加权威；`tool_audit.rs`、`trace.rs`、循环诊断仍提供派发与脱敏摘要。网关发送路径写入 generated／serialized／request_sent／provider_returned 四层见证。查询与下钻仍属 `C27`。

## 兼容

旧事件按兼容读取；不把旧事件当作当前执行事实。读边界单向兼容，不双写、不保留第二套权威状态。

## 测试

关键不变量与所需证据类别见 `V01`–`V07`；已有 `V03` 机械负例绑定当前指纹，当前 `verification.state=none`：机械负例不等于 `C27`／`V07` 诊断演练通过。

### C27 诊断查询与解释

## 输入与输出

- **输入**：Run／调用 ID、`C26` 事件与权威状态。
- **输出**：已知事实、直接失败、恢复结果、待证根因。
- **逻辑合同名称**：设计层名称，不是已存在的 Rust 类型或 IPC 字段；所属模块 `M09`。

## 决定权与不变量

- **决定权**：不把恢复耗尽当根因；缺事件必须报告缺口，不能默认执行成功。
- **不变量**：发现位置、已证实故障来源、关联影响与归因状态四者分离（`K17`）。
- **禁止行为**：越权改写其他模块的权威状态；把提议当作执行；把缺失当作成功。

## 状态

本组件持有的状态与其权威范围见上；持久状态只有 `M09` 的权威所有者可写，其余为进程内观察。

## 异常与恢复

查询失败明确报告失败，不返回空集冒充「没有问题」。失败分类使用稳定错误码，可恢复的错误按 `K16` 反馈后继续。

## 审计

诊断摘要、下钻路径与证据缺口即本组件的输出。不记录密钥、笔记正文、完整模型请求或私有推理。

## 源码落点

现有基础与处置：当前安全查询与事件投影；新增跨边界诊断视图，复用持久化基础。diagnostic-query 的目标合同不要求按组件新建文件；映射到多个责任组件的现有大文件应在迁移时删除被替代的重复判断。

## 兼容

历史运行无法完整诊断时明确标注，不推测缺失部分。读边界单向兼容，不双写、不保留第二套权威状态。
