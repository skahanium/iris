本文件登记 `V05`（厂商端点及协议兼容）的**授权前置**：要跑什么、要花什么、需要谁批。它**不是**验证结果。

2026-09-20 已按批准跑过 MiniMax-M3 原生搜索诊断探针（2 次调用），记录见 [2026-09-20 V05 MiniMax-M3 实网探针](./2026-09-20-v05-endpoint-live.md)。同日另跑 DeepSeek-Flash 原生搜索协议探针与适配器 live，记录见 [2026-09-20 V05 DeepSeek-Flash 原生搜索](./2026-09-20-v05-deepseek-native-search-live.md)。两份记录**都不关闭** `G03`／`Q17`／`D04`，也不把对应端点标为 V05 全矩阵已通过。窗口其余端点仍未获批、未运行。

- 判据来源：`V01`「厂商端点及协议兼容 = 协议测试 + 对应端点真实调用」。
- 承接方：`G03`（原生搜索事件的接入与端点适配）、`Q17`（原生搜索端点、混合续轮、费用与权限适配待验证）；两者由 `D04` 关闭。
- 明确不在 `D02` 关闭条件内：`D02` 已于 2026-09-19 收口，其关闭证据是**机械记录**（`V03`），不是本文件。

## 一、待验证端点矩阵（取自源码，不是厂商宣传）

来源：`config/llm-builtin-providers.json`（13 个内置厂商）与 `src-tauri/src/llm/model_catalog.rs`（33 个模型条目）。

| 协议族                            | 厂商                                                                                               | 模型数 | 说明                                                            |
| --------------------------------- | -------------------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------- |
| `OpenAiCompatibleChatCompletions` | deepseek、openai、google、zhipu、kimi、doubao、qwen、minimax、hunyuan、ernie、mimo、custom、ollama | 27     | 生产主力协议族                                                  |
| `AnthropicMessages`               | anthropic                                                                                          | 2      | 唯一使用 Messages 协议的厂商                                    |
| `ResponsesReserved`               | mimo                                                                                               | 4      | **全部是 ASR／TTS 模型且 `supports_tools = false`**，无工具端点 |

**一个必须先说清的事实**：当前生产目录里**没有**支持工具的 Responses 端点。因此「Responses 续轮保真」的逐端点 live 验证在本目录下**无法进行**；它只能在机械层（已有 `V03` 记录）与将来接入真实 Responses 端点后补。这一点不得被写成「Responses 已通过」。

## 二、每个端点要跑什么

对每个**支持工具**的端点，按协议族各跑一遍：

| 检查项                      | Chat Completions                                                  | Anthropic Messages               | 判据                                  |
| --------------------------- | ----------------------------------------------------------------- | -------------------------------- | ------------------------------------- |
| 正常结束                    | `finish_reason = stop` 保留                                       | `stop_reason = end_turn` 保留    | 不得被改写                            |
| 长度截断                    | `finish_reason = length` 到达验证边界                             | `stop_reason = max_tokens`       | 截断的工具调用不得派发                |
| 工具结束                    | `finish_reason = tool_calls` 仍派发                               | `stop_reason = tool_use` 仍派发  | 工具续轮成立                          |
| 缺失终止事件                | 缺 `finish_reason` → `unknown`，不填 `stop`                       | 缺 `stop_reason` → `unknown`     | 不得伪造正常结束                      |
| 尾事件                      | 仅 `[DONE]` 时仍保留事实                                          | `message_stop` 尾事件不填 `stop` | 同上                                  |
| 工具续轮字段                | assistant 回放 `tool_calls`；同 Provider 回放 `reasoning_content` | `tool_use`／`tool_result` 成对   | 必要字段不被静默丢弃                  |
| 稳定指令                    | system 指令在续轮保留                                             | 同上                             | 同上                                  |
| 原生搜索事件／引用（`G03`） | 供应商定义的实际搜索事件或结构化 grounding 元数据                 | 同左                             | **模型自行生成 URL 不算已搜**         |
| 计费与权限（`Q17`）         | 调用可关联到计费项；权限范围不因重试扩大                          | 同左                             | 不凭 `OpenAI-compatible` 标签判定能力 |

机械层的对应覆盖已存在（`V03`，见 `registry.json.verify` 的 `Q04`／`Q10`／`C11`／`K04` 记录）；本表要求的是**再加一次真实调用**。

## 三、需要你批准的四件事（缺一不可）

| #   | 需要批准                                                     | 为什么不能由施工方默认                       |
| --- | ------------------------------------------------------------ | -------------------------------------------- |
| 1   | **端点范围**：上表 13 个厂商中的哪些，各用哪个模型           | 每个端点都是真实付费调用；范围决定花费与耗时 |
| 2   | **费用上限**：本轮 live 验证的总费用上限（含原生搜索的计费） | 触及 `K06` 信封；不得由施工方自行扩大        |
| 3   | **凭据**：哪些厂商的 Key 已配置、允许本轮使用                | 凭据不进仓库；未配置的端点只能跳过并如实标注 |
| 4   | **原生搜索端点**：`G03` 要接哪一家的原生搜索                 | 需要厂商侧的搜索能力与计费口径确认           |

未获批准的端点一律**记为未运行**，不得用机械记录的绿灯替代。

## 四、授权后的执行与记录格式

授权后按端点逐条执行，产出 `docs/eval/results/<日期>-v05-endpoint-live.md`，每条至少记录：

- 厂商、模型、协议族、端点 URL 的主机名（不含 Key）；
- 使用的协议测试命令与本文件 §二 的检查项逐项结果；
- 真实调用的请求结构见证（沿用 `C26` 的脱敏格式：角色计数、字段是否存在、协议、关联标识；**不含笔记正文、Key、私有推理**）；
- 费用与耗时；失败项的稳定错误码与是否可重试；
- 明确的适用范围结论，例如「本端点机械与 live 均通过」／「仅机械通过，live 未运行」。

## 五、回退与边界

- 某端点 live 失败时，**保留机械结论**并如实记录协议／结果不足；不得归为「模型不支持」，也不得据此调整端点范围后重跑以掩盖失败。
- 未获费用授权时，本窗口保持「已登记、未运行」；`Q17`／`G03` 保持 `open`，`D04` 的端点验收证据保持缺失。
- 本文件不承诺任何端点会通过，也不设发布分数与延迟目标。
